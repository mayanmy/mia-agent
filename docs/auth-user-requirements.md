# Auth / User 登录权限需求文档

## 1. 背景与目标

Mia 当前运行在“本地可信网络”假设下：进入前端即可查看模型供应商、Agent、知识库、日志并发起对话。这不适合 20-50 人的内部团队长期使用，原因包括：

- 无法区分谁创建、修改或使用了 Agent。
- 模型 API Key、知识库文档、工具调用日志等管理能力没有访问边界。
- 用户离职或权限调整后无法立即收回访问权。
- 后续接入公开 WebApp、小程序或企业 SSO 时缺少稳定的身份基础。

本版本建立 Mia 的最小身份与权限闭环：本地账号登录、`Admin` / `User` 两种角色、会话注销、用户禁用和后台接口鉴权。

一句话目标：

> 只有已登录且拥有相应角色的团队成员，才能访问 Mia 的内部工作台和 API。

## 2. 范围

### 2.1 v1 必须完成

- 用户账号表与角色字段。
- 管理员初始化方式。
- 邮箱 + 密码登录。
- 当前登录用户查询。
- 刷新会话、退出当前设备、退出全部设备。
- Access Token 校验、路由鉴权和 `CurrentUser` 获取方式。
- `Admin` / `User` 两级权限校验。
- Admin 用户管理：列表、创建、编辑角色、重置密码、启用/禁用、注销用户全部会话。
- 前端登录页、登录态恢复、无权限页、退出入口和用户信息展示。
- 内部管理 API 与 SSE 对话接口均受鉴权保护。
- 登录成功、登录失败、用户禁用、密码重置、会话撤销等安全审计日志。

### 2.2 v1 明确不做

- 企业 SSO、LDAP、OAuth/OIDC 登录。
- 多租户、Workspace 级隔离。
- 复杂 RBAC、自定义角色或细粒度菜单权限。
- 自助注册、邮箱验证码、找回密码邮件。
- MFA、设备指纹、异地登录提醒。
- 对外 API Key、公开 Agent 访问控制和小程序用户身份映射。

这些能力在 v2 以后以现有 `User`、`AuthSession` 和统一 Guard 为基础扩展，v1 不提前引入复杂身份平台。

## 3. 角色与权限

### 3.1 角色定义

| 角色    | 说明                                                     |
| ------- | -------------------------------------------------------- |
| `ADMIN` | 平台管理员，可使用全部工作台模块，并负责成员管理。       |
| `USER`  | 普通团队成员，可使用和管理除成员管理外的全部工作台模块。 |

### 3.2 v1 权限矩阵

| 能力                             | Admin | User |
| -------------------------------- | ----- | ---- |
| 登录、查看自己的账号、退出       | 是    | 是   |
| 查看和使用已启用 Agent           | 是    | 是   |
| 发起普通/流式对话                | 是    | 是   |
| 查看模型供应商与模型配置         | 是    | 是   |
| 管理模型供应商与模型配置         | 是    | 是   |
| 创建、编辑、删除、发布 Agent     | 是    | 是   |
| 查看、上传、重建、删除知识库文档 | 是    | 是   |
| 查看工具定义、工具调用日志       | 是    | 是   |
| 查看日志页                       | 是    | 是   |
| 管理用户与重置密码               | 是    | 否   |

说明：v1 采用团队共建工作台模式。`USER` 与 `ADMIN` 的唯一功能差异是成员管理；后续如需控制具体资源的维护权限，再增加 `EDITOR` 或 Agent 级协作者，不在本次范围内。

### 3.3 匿名访问例外

已发布 Agent 的公开分享页与其公开聊天 API 是未来独立功能，不能使用内部工作台的登录态替代访问控制。v1 保留现有公开路径的匿名能力：

- `GET /agents/shared/:token`
- 已发布 Agent 的分享页面路由 `/share/agents/:token`

其余 `/api/v1/*` 内部接口默认必须登录。公开 Chat 的防刷、密码、域名限制会在“公开 WebApp”版本单独设计。

## 4. 用户流程

### 4.1 初始化第一个管理员

1. 部署人员执行受控的管理员初始化命令，传入邮箱和一次性初始密码。
2. 系统仅在没有可用管理员时创建账号；重复执行必须报错，不覆盖已有账号。
3. 部署人员使用该账号登录后，立即在成员管理页面创建其他成员并修改初始密码。

### 4.2 登录与会话恢复

1. 用户访问内部工作台，未登录时跳转 `/login`。
2. 输入邮箱和密码后，前端获得短期 Access Token，浏览器同时保存 HttpOnly Refresh Cookie。
3. 前端加载当前用户资料并跳转到其默认页面：Admin 到 Agent 列表，User 到对话页。
4. Access Token 失效时，前端调用刷新接口获取新 Token；刷新失败则清空本地状态并回到登录页。

### 4.3 管理员禁用用户

1. Admin 在成员列表禁用目标用户。
2. 系统写入 `disabled_at` 并撤销该用户全部 Refresh Session。
3. 被禁用用户下一次请求立即被 Access Token Guard 拒绝；已有 SSE 连接在本轮实现中最迟于下一次心跳或请求结束后失效。
4. 管理员可再次启用账号；启用不会恢复旧会话，用户必须重新登录。

### 4.4 退出登录

- 退出当前设备：撤销当前 Refresh Session，清除 Refresh Cookie 和内存中的 Access Token。
- 退出全部设备：撤销该用户所有未过期 Session，当前设备也回到登录页。

## 5. 体验要求

- 登录页只展示必要字段：邮箱、密码、登录按钮和错误提示。
- 密码错误、账号不存在、账号禁用统一展示为“邮箱或密码错误，或账号已被禁用”，避免泄漏账号存在性。
- 401 自动跳登录；403 显示“没有权限访问此页面”，不显示空白页或通用 `internal server error`。
- User 登录后不显示模型供应商、知识库、日志等无权限菜单。
- 正在进行的 SSE 聊天因登录态失效时，前端显示明确错误并恢复输入框，不允许一直停在“生成中”。

## 6. 安全与数据要求

- 密码只保存 Argon2id 哈希，不保存明文、可逆加密文本或日志。
- Access Token 有效期短，默认 15 分钟；Refresh Session 默认 30 天并可服务端撤销。
- Refresh Token 仅通过 `HttpOnly`、`SameSite=Lax` Cookie 保存；生产环境必须启用 `Secure`。
- Access Token 仅驻留在前端内存，页面刷新时通过 Refresh Cookie 恢复，禁止写入 `localStorage` / `sessionStorage`。
- Refresh Token 在数据库中只保存哈希值；数据库泄漏不能直接复用会话。
- 用户邮箱按小写规范化后唯一；密码最少 8 位，v1 要求包含字母和数字。
- 禁用、改角色、重置密码、撤销会话必须记录审计事件，日志不写密码、Token 或完整 Cookie。

## 7. 验收标准

1. 未登录访问内部 API 返回统一 401，访问内部页面跳转登录页。
2. 登录成功后 Admin 能访问所有已有后台页面和接口。
3. User 仅能查看可用 Agent 并对话，直接请求后台管理 API 返回 403。
4. 用户被禁用或重置密码后，旧会话不再可继续访问。
5. 刷新页面后仍能恢复有效会话；退出后刷新也不会自动重新登录。
6. 公开分享 Agent 页面不因为内部认证上线而失效。
7. 登录、刷新、退出、禁用和权限拒绝至少覆盖成功与失败测试路径。

## 8. 迭代规划

### v1.0：本地账号与两级权限

完成本需求文档定义的全部能力，作为所有内部 API 的统一访问门槛。

### v1.1：成员使用体验与审计完善

- 用户自助修改密码。
- 管理员查看活跃会话和最近登录时间。
- 登录失败限流与短时锁定。
- Agent / 知识库 / 模型的操作审计列表。

### v2：企业身份与资源级权限

- OIDC / 企业 SSO。
- `EDITOR` 角色与 Agent、知识库协作者。
- API Key / 服务账号，供小程序和业务后端安全调用。
- 公开 WebApp 的访问密码、域名白名单、访问统计。
