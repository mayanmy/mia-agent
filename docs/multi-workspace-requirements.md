# Mia 多团队 Workspace 需求文档

## 1. 背景

Mia 当前按单团队、本地部署设计：所有已登录成员共享模型供应商、Agent、知识库、日志等工作台资源，只有成员管理受 Admin/User 角色限制。

当一个 Mia 实例需要服务多个彼此独立的团队时，不能继续按“全局共享资源”处理。否则团队 A 的模型密钥、Agent、知识库内容、文档文件和日志可能被团队 B 看到或修改，形成严重的数据隔离问题。

本需求引入 Workspace 作为 Mia 的一级数据边界。一个 User 可以加入多个 Workspace；同一 Workspace 内的成员共享资源，不同 Workspace 之间默认完全隔离。

## 2. 目标与范围

### 2.1 目标

- 支持在一个 Mia 实例内创建和管理多个 Workspace。
- 支持一个用户加入多个 Workspace，并切换当前工作团队。
- 保证模型供应商、Agent、知识库、文件、向量、日志等资源只在所属 Workspace 内可见和可操作。
- 保持当前单团队使用体验：只有一个 Workspace 的用户不需要额外选择团队。
- 将角色从全局 User 属性迁移到 Workspace 成员关系，支持每个团队独立授权。

### 2.2 本期范围

- Workspace 创建、列表、切换、基础资料编辑。
- Workspace 成员邀请、角色调整、移除成员。
- Workspace 范围内的数据隔离和接口鉴权。
- 现有单团队数据迁移至“默认团队”。
- 当前工作台模块在团队内的资源共享：模型供应商、模型配置、Agent、知识库、对话、工具调用日志。

### 2.3 非目标

- 不做组织层级、部门树、项目空间嵌套。
- 不做跨 Workspace 的 Agent、知识库、模型配置共享。
- 不做复杂自定义 RBAC、字段级权限或资源级 ACL。
- 不做跨 Workspace 的聚合运营报表。
- 不做多区域部署、独立数据库实例或付费计量。

## 3. 核心概念

| 概念            | 说明                                                               |
| --------------- | ------------------------------------------------------------------ |
| User            | 全局登录身份。邮箱在 Mia 实例内唯一，可加入多个 Workspace。        |
| Workspace       | 一个独立团队的数据、配置和权限边界。                               |
| WorkspaceMember | User 与 Workspace 的成员关系，记录角色、加入时间和状态。           |
| 当前 Workspace  | 当前请求和当前工作台页面所使用的 Workspace，上下文必须明确传递。   |
| 外部终端用户    | 调用已发布 Agent 的用户，不是 Mia 工作台成员，不可访问工作台资源。 |

## 4. 角色与权限

角色属于 WorkspaceMember，而非 User。

| 能力                             | OWNER | MANAGER | MEMBER              |
| -------------------------------- | ----- | ------- | ------------------- |
| 查看、使用团队 Agent/知识库/日志 | 是    | 是      | 按模块开放          |
| 创建、编辑 Agent                 | 是    | 是      | 仅本人创建项        |
| 创建、编辑 HTTP Tool             | 是    | 是      | 仅本人创建项        |
| 查看模型供应商和模型配置         | 是    | 是      | 仅安全模型选项      |
| 编辑模型 API Key、删除供应商     | 是    | 是      | 否                  |
| 邀请、移除成员、修改角色         | 是    | 否      | 否                  |
| 转让团队所有权                   | 是    | 否      | 否                  |
| 删除 Workspace                   | 是    | 否      | 否                  |

说明：当前 Mia 允许 MEMBER 创建并管理本人的 Agent 和 HTTP Tool。模型供应商密钥属于高风险凭证，仅 OWNER/MANAGER 可修改。

## 5. 功能需求

### 5.1 Workspace 管理

- 用户首次注册或管理员初始化时，系统创建一个默认 Workspace，并指定 OWNER。
- OWNER 可创建新的 Workspace，填写名称和描述。
- 当前用户可查看自己加入的 Workspace 列表。
- 用户可以切换当前 Workspace；切换后页面数据、缓存和后续 API 请求必须切换到新团队上下文。
- OWNER 可修改团队名称和描述，可转让所有权，可删除空 Workspace。

### 5.2 成员管理与邀请

- 成员邀请必须指定目标 Workspace 和成员角色。
- 同一邮箱可以被邀请到多个 Workspace；邀请唯一性以 `(workspaceId, email)` 为准。
- 接受邀请时：已有 User 仅新增成员关系；不存在 User 时设置密码并创建 User 后新增关系。
- ADMIN 不可删除或降级最后一个 OWNER；OWNER 转让必须显式确认。
- 移除成员后，该成员立刻不能再访问该 Workspace，但其其他 Workspace 会话不受影响。

### 5.3 资源隔离

下列资源必须归属一个且仅一个 Workspace：

- 模型供应商、模型配置、默认模型设置。
- Agent、Agent 工具绑定、Agent 知识库绑定、发布配置。
- 知识库、文档、Chunk、Embedding、向量 namespace、上传文件。
- 工具调用日志、检索日志、对话日志和后台索引任务。

同一 Workspace 的成员按角色规则共享资源；跨 Workspace 的查询、绑定、读取、更新、删除均不得成功。

### 5.4 对话与外部发布

- 工作台对话必须使用当前 Workspace 的 Agent，不能通过伪造 Agent ID 使用其他 Workspace 的资源。
- 已发布 Agent 的 share token 仍可直接解析其所属 Agent 和 Workspace，不要求工作台成员登录。
- 外部对话会话和日志必须记录 Workspace ID，便于审计和限流。
- 外部调用 token 不授予模型供应商、知识库、成员管理等工作台能力。

## 6. 页面与交互

- 左侧导航顶部展示当前 Workspace 名称和切换入口；只有一个 Workspace 时保持紧凑展示。
- 成员管理页面改为“当前团队成员”，不再展示平台所有用户。
- 所有列表、详情、弹窗仅展示当前 Workspace 的可选模型、Agent 和知识库。
- 切换 Workspace 后清空上一个团队的页面内存数据、进行中的对话和缓存，再加载新团队数据。
- 无当前 Workspace、成员关系失效或无权限时，展示明确引导，不显示其他团队资源。

## 7. 验收标准

- 用户 A 加入 Workspace A、B 后，可分别看到两个团队独立的资源。
- 用户 B 只加入 Workspace B，无法通过 URL、API ID、Agent ID 或知识库 ID 读取 Workspace A 数据。
- Workspace A 的模型配置不能绑定到 Workspace B 的 Agent 或知识库。
- 移除成员后，该成员的旧 Access Token 无法继续访问被移除 Workspace 的接口。
- 删除或转让 Workspace 时保留必要审计日志，并阻止删除仍存在资源或成员的 Workspace。
- 从单团队升级后，已有资源全部归入默认 Workspace，功能和数据完整可用。

## 8. 发布建议

多团队是架构级能力，不应在已有多个外部团队数据后再临时补做。当前单团队版本可先保留本方案；首次需要服务两个相互隔离团队之前，必须完成数据库迁移、接口隔离和跨团队安全测试后再上线。
