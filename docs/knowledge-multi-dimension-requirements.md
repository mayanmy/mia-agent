# 知识库多向量维度需求文档

## 1. 背景

Mia 当前知识库向量表使用固定结构：

```sql
embedding vector(1536)
```

这意味着所有知识库都必须使用 1536 维 Embedding 模型。实际使用中，不同模型供应商返回的向量维度并不一致，例如部分 OpenAI-compatible 或本地模型可能返回 1024 维、768 维或 3072 维。

当知识库选择了 1024 维 Embedding 模型时，索引文档会失败：

```text
expected 1536 dimensions, not 1024
```

这不是文档内容问题，而是数据库向量列维度和 Embedding 模型输出维度不匹配。为了让 Mia 支持更多模型供应商，同时保持知识库检索稳定，需要支持“不同知识库使用不同向量维度”。

## 2. 问题定义

当前全局固定 1536 维会带来这些问题：

- 用户无法使用 1024 维、768 维等 Embedding 模型创建可用知识库。
- 知识库索引失败原因容易被误解为文档解析失败。
- Agent 绑定多个知识库时，无法同时检索不同 Embedding 模型构建的知识库。
- 后续接入更多 OpenAI-compatible、本地模型或国产模型时会被数据库结构限制。

需要解决的是：

> 不同知识库可以使用不同 Embedding 模型和向量维度，但同一个知识库内部必须保持向量维度一致。

## 3. 产品目标

### 3.1 核心目标

- 创建知识库时可以选择 Embedding 模型。
- 知识库保存所选 Embedding 模型和对应向量维度。
- 同一个知识库内所有文档必须使用相同 Embedding 模型维度索引。
- 不同知识库可以使用不同向量维度。
- Agent 可以绑定多个不同维度的知识库并完成检索。
- 维度不匹配时给出明确、可操作的错误提示。

### 3.2 非目标

v1 不做以下能力：

- 同一个知识库内混用多个 Embedding 模型。
- 用户手动输入向量维度。
- 自动推断所有模型维度并长期缓存。
- 知识库在线切换 Embedding 模型并自动重建。
- 多模型检索结果复杂归一化和 rerank。
- 向量索引自动调优。

## 4. 用户价值

- 管理员可以按模型供应商选择合适的 Embedding 模型，不再被 1536 维限制。
- 本地模型和国产模型更容易接入 Mia 知识库。
- 索引失败原因更清楚，排查成本更低。
- Agent 可以组合多个来源不同的知识库，提高知识覆盖范围。
- 后续做知识库重建、模型迁移和检索质量优化有稳定基础。

## 5. 核心规则

### 5.1 知识库级维度锁定

创建知识库时确定：

- `embedding_model_config_id`
- `embedding_dimension`

知识库创建后，文档上传、重建索引和检索都必须沿用该配置。

### 5.2 同库维度一致

同一个知识库内：

- 所有 chunk 的 embedding 维度必须等于 `knowledge_base.embedding_dimension`。
- 如果模型返回维度不一致，文档索引失败。
- 失败原因必须明确显示需要的维度和实际返回维度。

### 5.3 不同库可以不同维度

不同知识库可以分别使用：

- 1536 维 Embedding 模型。
- 1024 维 Embedding 模型。
- 后续支持的其他维度模型。

### 5.4 检索按 Embedding 模型分组

Agent 绑定多个知识库时，不能简单用一个 query embedding 检索所有库。

检索必须按 `embedding_model_config_id` 分组：

```text
知识库 A：model-a，1536 维
知识库 B：model-b，1024 维
知识库 C：model-a，1536 维

检索时：
model-a 生成一次 query embedding，查 A/C
model-b 生成一次 query embedding，查 B
合并结果后返回给 Chat
```

原因：即使两个模型维度相同，向量空间也不一定兼容，因此分组依据优先是 Embedding 模型，而不是单纯维度。

## 6. 用户流程

### 6.1 创建知识库

1. 管理员进入知识库页面。
2. 点击创建知识库。
3. 填写名称和描述。
4. 选择 Embedding 模型。
5. 页面展示该模型的向量维度。
6. 保存知识库。
7. 系统记录知识库的 Embedding 模型和向量维度。

### 6.2 上传文档

1. 管理员进入知识库文档列表。
2. 上传文档。
3. 系统使用知识库绑定的 Embedding 模型生成向量。
4. 系统校验返回维度是否等于知识库维度。
5. 校验通过则写入对应向量存储。
6. 校验失败则文档状态为失败，并展示可读错误。

### 6.3 Agent 检索

1. 用户向 Agent 提问。
2. Chat 加载 Agent 绑定的知识库。
3. Retrieval 按 Embedding 模型分组。
4. 每组生成一次 query embedding。
5. 每组查询对应维度的向量表。
6. 合并候选片段。
7. 返回给 Chat 注入 Prompt，并展示引用来源。

## 7. 页面需求

### 7.1 知识库创建表单

需要展示：

- 知识库名称。
- 描述。
- Embedding 模型选择器。
- 模型供应商。
- 模型名称。
- 向量维度。

提示文案：

```text
Embedding 模型决定该知识库的向量维度。创建后如需更换模型，需要重建知识库索引。
```

### 7.2 知识库列表

建议展示：

- 知识库名称。
- 文档数。
- chunk 数。
- Embedding 模型。
- 向量维度。
- 最近索引时间。
- 状态。

### 7.3 文档失败原因

维度不匹配时展示：

```text
Embedding 向量维度不匹配：当前知识库需要 1536 维，但模型返回 1024 维。请更换匹配维度的 Embedding 模型，或创建新知识库后重新上传。
```

## 8. 版本拆分

### 8.1 v1：多维度最小闭环

必须做：

- 知识库保存 `embedding_dimension`。
- 创建知识库时确定 Embedding 模型和维度。
- 支持 1536 和 1024 两类向量维度。
- 索引时校验同库维度一致。
- 按维度写入对应向量表。
- 检索时按 `embedding_model_config_id` 分组。
- 前端展示知识库的 Embedding 模型和维度。
- 维度不匹配错误可读。

暂不做：

- 知识库切换 Embedding 模型。
- 自动重建全库索引。
- 更多维度的页面配置。
- 检索分数归一化。

### 8.2 v1.1：配置体验增强

可做：

- 模型配置中维护 `embedding_dimension`。
- 模型测试时自动探测 Embedding 维度。
- 创建知识库时只展示可用 Embedding 模型。
- 已创建知识库禁用 Embedding 模型编辑。
- 文档重试时提示使用的是哪个 Embedding 模型。

### 8.3 v2：知识库模型迁移

可做：

- 支持知识库更换 Embedding 模型。
- 更换模型后触发全库重建索引。
- 展示重建进度。
- 失败后支持回滚或继续重试。
- 支持更多向量维度分表。

### 8.4 v3：检索质量优化

可做：

- 跨模型检索结果分数归一化。
- rerank 合并多组检索结果。
- 按知识库设置 topK 和相似度阈值。
- 向量索引 HNSW/IVFFlat 优化。
- 大规模知识库分区和归档。

## 9. 验收标准

### 9.1 索引验收

- 1536 维知识库上传文档成功。
- 1024 维知识库上传文档成功。
- 1024 维模型不能写入 1536 维知识库。
- 维度不匹配时文档状态为失败。
- 失败原因包含需要维度和实际维度。

### 9.2 检索验收

- Agent 绑定单个 1536 维知识库可检索。
- Agent 绑定单个 1024 维知识库可检索。
- Agent 同时绑定 1536 和 1024 维知识库可检索。
- 检索结果包含正确来源。
- 不出现 pgvector 原始维度错误。

### 9.3 页面验收

- 知识库创建时能看到 Embedding 模型维度。
- 知识库列表能看到模型和维度。
- 文档失败原因可读。
- 用户不需要理解 pgvector 原始错误。

## 10. 风险与约束

- 不同 Embedding 模型的相似度分数不可直接等价，v1 合并结果时只做简单排序和截断，后续需要 rerank。
- 按维度分表会增加代码映射复杂度，但能保留 pgvector 固定维度索引能力。
- 现有 1536 维数据需要迁移或保留兼容。
- 创建知识库后随意更换 Embedding 模型会破坏已有索引，v1 必须禁止直接修改。
