# Mia Chat 优化技术方案

## 1. 背景与目标

当前 Chat 已支持 SSE 流式回答、停止生成、持久会话、附件、知识检索、引用来源和工具调用。主要问题是运行过程与最终答案层级混杂、检索来源重复展示、失败只用全局提示、生成状态不够明确，以及历史消息无法完整恢复运行元数据。

本方案目标：

1. 优先提升回答阅读体验和失败恢复能力。
2. 保留管理员排查 RAG、工具和模型问题所需的信息。
3. 分阶段扩展消息持久化，避免一次性引入高风险数据库变更。
4. 将 ChatPage 中的 SSE、会话与消息归并职责逐步拆到 hooks。

## 2. 设计原则

- 答案优先：默认突出最终回答，运行过程折叠展示。
- 渐进披露：普通用户看到可读状态，原始 score、chunkId 等放入详情。
- 错误可恢复：失败必须留在消息流中，并提供重试入口。
- 历史可重放：持久会话最终应恢复附件、来源、工具、耗时和错误。
- 高风险工具不自动重放：重新生成不得隐式重复已经执行的写操作。

## 3. 分阶段实施

### 阶段一：对话阅读与失败恢复（本轮实现）

- 检索过程默认折叠，收起时只显示命中数量和耗时。
- 检索来源与回答底部参考资料不再同时完整展开。
- 原始 score 改为用户可读的相关度百分比。
- 回答生成期间持续显示状态，不在首个 token 后消失。
- 失败、停止状态写入 assistant 消息元数据，不再污染回答正文。
- 失败和停止消息提供“重试”；执行过工具的回答禁止自动重放。
- Assistant 正文限制舒适阅读宽度。

验收标准：

- RAG 回答默认只占用一行运行过程摘要。
- 流式正文开始后仍显示“正在生成”。
- 网络或模型失败后，时间线保留错误卡片，可重新提交原问题。
- 停止生成后正文保持原样，并显示独立停止状态。

### 阶段二：完整历史消息（已完成核心快照）

- [x] 复用现有消息 `metadata JsonB` 保存运行快照，无需新增迁移。
- [x] 持久化检索来源、工具事件、模型、usage、耗时和 request_id。
- [x] 历史接口返回消息 metadata，刷新后恢复检索、引用和工具过程。
- [ ] 附件改为文件存储引用后持久化，禁止把图片 data URL 写入消息表。
- [x] 会话列表接入 `nextCursor`，支持加载 30 条之后的会话。
- [x] 增加已加载会话搜索和今天/昨天/近 7 天/更早分组。
- [ ] 失败和取消快照需先明确是否进入模型上下文，再设计独立运行记录关联。

现有 schema 已包含 `metadata JsonB`，因此核心快照无需数据库迁移；附件持久化仍需后续设计文件存储引用。

### 阶段四：代码结构治理

将 `ChatPage.tsx` 的职责拆为：

```text
hooks/useChatSessions.ts       会话列表与生命周期
hooks/useChatStream.ts         SSE、发送、停止和重试
hooks/useChatMessageEvents.ts  token、检索、工具和错误归并
```

按纯函数、消息展示、状态 hook、会话 hook 的顺序拆分，每一步保持用户行为不变。

当前进度：已提取 `useChatMessageEvents`，SSE 消息数组归并不再堆叠在路由页；会话与流生命周期将在后续保持行为不变地继续拆分。

## 4. 数据与安全约束

- 重试只重新提交用户输入，不自动复用旧 assistant 输出。
- 已执行工具的重新生成必须提示可能重复操作；阶段一仅对无工具调用的回答开放重新生成。
- 用户可见错误不包含密钥、上游原始响应或堆栈。
- request_id 可展示和复制，但不作为鉴权凭据。
- 引用编号只有在模型输出能和来源稳定映射后才启用；此前使用“参考资料”。

## 5. 验证

每阶段至少运行：

```bash
npm run typecheck
npm run lint
npm run build
```

阶段二还需覆盖消息元数据写入、历史分页、取消不写伪完整回答以及旧数据兼容测试。
